# Обзор проекта

## Назначение

AutoPartsSync - внутреннее веб-приложение для магазина автозапчастей. По текущему состоянию кода оно объединяет два рабочих направления:

- поиск аналогов по артикулу с получением остатков из внешней системы;
- ведение клиентских карточек и связанных автомобилей.

Проект не подтверждает полноценную ERP- или CRM-модель. Документация ниже описывает только то, что видно в коде.

## Ключевые понятия

### Client

Модель `Client` хранит:

- имя;
- телефон;
- комментарий;
- дату создания.

Используется как клиентская карточка в приложении `counterparties`.

### Car

Модель `Car` хранит:

- ссылку на клиента;
- марку;
- модель;
- госномер;
- VIN;
- комментарий;
- дату создания.

Отношение: один `Client` -> много `Car`.

### Артикул детали

Артикул используется в приложении `analogs` как входной параметр поиска по внешним API.

### Brand

Бренд детали используется как часть поиска через ABCP. По текущему коду бренд определяется внешним сервисом и затем участвует в поиске артикулов.

### Остатки

Остатки получаются из МойСклад после сопоставления найденных артикулов с ассортиментом.

## Основные сценарии

### 1. Поиск аналогов и остатков

Сотрудник:

- открывает страницу поиска;
- вводит артикул;
- получает список найденных артикулов и брендов;
- видит остатки по тем позициям, которые удалось сопоставить с МойСклад.

### 2. Ведение клиентов

Сотрудник:

- открывает workspace контрагентов;
- ищет клиента по имени или телефону;
- создает, обновляет или удаляет клиентскую карточку.

### 3. Ведение автомобилей клиента

Сотрудник:

- выбирает клиента;
- добавляет автомобиль;
- редактирует данные автомобиля;
- удаляет автомобиль;
- использует поиск по VIN, госномеру, марке и модели.

## Границы текущей реализации

Подтверждено:

- серверный HTML UI;
- авторизация пользователей;
- CRUD по клиентам и автомобилям;
- интеграция с ABCP;
- интеграция с МойСклад для чтения ассортимента и остатков.

Не подтверждено:

- заказы;
- отгрузки;
- поставщики как полноценная действующая сущность;
- закупки;
- складские документы;
- подбор по совместимости детали с автомобилем;
- REST API;
- фоновые синхронизации.

## Известные assumptions

- Название `counterparties` шире фактической модели, потому что в коде активна только клиентская часть.
- В миграции `0001_initial` у `Client` было поле `type` со значениями `customer` и `supplier`, но затем оно удалено. Это показывает исторический след доменной идеи, но не доказывает, что поддержка поставщиков есть сейчас.
- Локальный `.env` содержит переменную `MS_LOGIN`, но код ее не использует.

## Что неясно

- Нужно ли проекту хранить поставщиков как сущность.
- Должен ли проект использовать другую БД вместо SQLite.
- Являются ли `TIME_ZONE='UTC'` и `LANGUAGE_CODE='en-us'` осознанными настройками.
- Нужен ли старый detail-template клиента или он остался после редизайна.

## Вывод

На текущий момент AutoPartsSync - это не общая операционная платформа “всего магазина”, а компактный Django-монолит с двумя подтвержденными доменными вертикалями:

- поиск аналогов и остатков;
- клиентские карточки с автомобилями.

Любое расширение описания проекта за эти границы нужно маркировать как план или гипотезу, а не как текущее состояние.
