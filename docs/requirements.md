# Требования к текущей версии AutoPartsSync

## 1. Назначение системы

- Система должна предоставлять сотрудникам магазина автозапчастей единое рабочее пространство для поиска аналогов деталей и ведения клиентской базы.
- Система должна помогать быстро находить информацию по детали по артикулу и одновременно поддерживать работу с карточками клиентов и их автомобилей.
- Система должна использоваться только как внутренний рабочий инструмент сотрудников.

## 2. Пользователи системы

- Сотрудник магазина автозапчастей.
- Сотрудник кассы или стойки обслуживания.
- Сотрудник, который ведет клиентскую базу и историю автомобилей клиента.

## 3. Основные сценарии использования

### 3.1. Вход в систему

- Пользователь открывает систему.
- Система запрашивает учетные данные.
- После успешного входа система предоставляет доступ к рабочим разделам.
- Если вход не выполнен, защищенные разделы должны оставаться недоступными.

### 3.2. Поиск аналогов детали по артикулу

- Пользователь вводит артикул детали.
- Система выполняет поиск по введенному артикулу.
- Если по артикулу найден один однозначный бренд, система показывает найденные аналоги.
- Для каждого найденного аналога система показывает:
- артикул;
- бренд;
- доступный остаток.
- Если совпадений нет, система должна сообщать, что по запросу ничего не найдено.
- Если запрос еще не введен, система должна показывать пустое состояние без результатов.

### 3.3. Просмотр базы клиентов

- Пользователь открывает раздел клиентов.
- Система показывает список клиентов.
- Для каждого клиента система показывает:
- имя;
- телефон, если он указан;
- количество связанных автомобилей;
- признак наличия комментария, если комментарий заполнен.
- Пользователь может выбрать клиента из списка и открыть его рабочую карточку.

### 3.4. Поиск клиента или автомобиля

- Пользователь вводит поисковый запрос в разделе клиентов.
- Система должна искать совпадения по следующим данным:
- имя клиента;
- телефон клиента;
- марка автомобиля;
- модель автомобиля;
- государственный номер автомобиля;
- VIN автомобиля.
- Система должна показывать только тех клиентов, которые соответствуют запросу.
- Если у выбранного клиента совпадение найдено по автомобилю, система должна выделять соответствующий автомобиль в списке.

### 3.5. Создание карточки клиента

- Пользователь может создать нового клиента.
- При создании клиента система должна позволять указать:
- имя;
- телефон;
- комментарий.
- После сохранения система должна открыть созданную карточку клиента.
- Пользователь должен иметь возможность сразу перейти к добавлению автомобиля для нового клиента.

### 3.6. Редактирование и удаление клиента

- Пользователь должен иметь возможность изменить данные клиента.
- Пользователь должен иметь возможность удалить клиента.
- При удалении клиента система должна удалять и связанные с ним автомобили.

### 3.7. Добавление автомобиля клиенту

- Пользователь должен иметь возможность добавить автомобиль в карточку выбранного клиента.
- Для автомобиля система должна позволять указать:
- марку;
- модель;
- государственный номер;
- VIN;
- комментарий.
- После сохранения автомобиль должен появляться в списке автомобилей выбранного клиента.

### 3.8. Редактирование и удаление автомобиля

- Пользователь должен иметь возможность изменить данные автомобиля.
- Пользователь должен иметь возможность удалить автомобиль из карточки клиента.
- После удаления автомобиля система должна сохранять саму карточку клиента.

## 4. Что должен уметь продукт

- Предоставлять доступ к системе только авторизованным сотрудникам.
- Показывать отдельный раздел поиска деталей и отдельный раздел работы с клиентами.
- Искать аналоги деталей по артикулу.
- Показывать по найденным аналогам бренд и остаток.
- Хранить клиентские карточки.
- Хранить несколько автомобилей у одного клиента.
- Показывать карточку выбранного клиента вместе со связанными автомобилями.
- Искать клиентов и автомобили в едином поисковом поле.
- Позволять создавать, редактировать и удалять клиентов.
- Позволять создавать, редактировать и удалять автомобили клиента.
- Показывать пустые состояния и сообщения о результате действий пользователя.

## 5. Ограничения текущей версии

- Система предназначена только для внутреннего использования сотрудниками.
- Работа с системой возможна только после авторизации.
- Поиск аналогов выполняется только по артикулу.
- Система показывает результаты аналогов только в случае однозначно определенного бренда по введенному артикулу.
- В карточке клиента хранится только базовая информация без расширенной истории взаимодействий.
- В карточке автомобиля хранится только базовая идентификационная информация и комментарий.
- Удаление клиента приводит к удалению всех его автомобилей.
- Текущая версия ориентирована на ручную работу пользователя через веб-интерфейс.

## 6. Что не входит в текущую версию

- Оформление заказов и продаж.
- Бронирование или резервирование товара.
- Корзина, счет, накладная или другие торговые документы.
- Управление ценами и прайс-листами.
- История изменений по клиенту или автомобилю.
- История поисковых запросов по деталям.
- Сохранение избранных или часто используемых артикулов.
- Массовый импорт или экспорт клиентов и автомобилей.
- Разграничение прав доступа по ролям сотрудников.
- Самостоятельная регистрация пользователей.
- Личный кабинет клиента.
- Уведомления клиентам.
- Прикрепление файлов, фотографий или документов.
- Подбор деталей по VIN как отдельный сценарий.
- Сравнение нескольких вариантов аналогов по дополнительным параметрам.
- Работа с несколькими складами в интерфейсе пользователя.
- Аналитика, отчеты и дашборды.

## 7. Планируемые требования к доступу сотрудников

### 7.0. Утвержденная модель доступа

- Для employee-auth первой версии утверждена кастомная модель пользователя Django с email как основным идентификатором входа.
- Целевые статусы сотрудника фиксируются как `created`, `active` и `deactivated`.
- Управление ролями и доступом в первой версии строится на стандартных Django Groups и Permissions без замены встроенного механизма авторизации.
- Все последующие этапы employee-auth должны опираться на это решение и не возвращаться к варианту со стандартным `auth.User` как целевой модели.

### 7.1. Общие правила доступа

- Доступ к системе остается закрытым и доступен только сотрудникам, которых создал администратор системы.
- Публичная регистрация пользователей запрещена.
- Вход сотрудника выполняется только по email и паролю.
- Доступ к Django admin остается только у администраторов системы.

### 7.2. Создание сотрудника

- Администратор системы должен иметь возможность создать учетную запись сотрудника по email.
- После создания сотрудник должен иметь статус `created`.
- Email сотрудника считается подтвержденным в момент создания администратором.
- Для сотрудника должен выпускаться одноразовый токен установки пароля с ограниченным сроком действия 24 часа.
- Администратор должен получать готовую ссылку приглашения в интерфейсе employee-management и копировать ее вручную вне системы.

### 7.3. Активация сотрудника

- Сотрудник должен активировать доступ только через одноразовую ссылку установки пароля.
- После успешной установки пароля сотрудник должен переходить в статус `active`.
- После успешной активации сотрудник должен входить в систему через обычную страницу логина.
- Автоматический вход после установки пароля не требуется.

### 7.4. Повторная выдача ссылки

- Повторную выдачу ссылки может выполнять только администратор системы.
- При повторной выдаче должен создаваться новый токен.
- Предыдущий токен должен немедленно становиться недействительным.
- В один момент времени у сотрудника может существовать только одно активное приглашение.
- Формат приглашения для первой версии фиксируется как обычный URL без дополнительной подписи данных сверх случайного одноразового токена.

### 7.5. Деактивация сотрудника

- Администратор системы должен иметь возможность перевести сотрудника в статус `deactivated`.
- Деактивированный сотрудник не должен иметь возможность входить в систему.
- При деактивации должны завершаться активные сессии сотрудника.

### 7.6. Сброс и изменение учетных данных

- В первой версии самостоятельное восстановление пароля сотрудником не поддерживается.
- Если сотруднику нужен новый доступ или новая ссылка, сценарий выполняется только через администратора системы.
- При смене email сотрудника новый email должен подтверждаться через новый сценарий приглашения.

### 7.7. Требования безопасности

- Токен установки пароля должен быть одноразовым.
- Токен должен иметь конечный срок жизни.
- После использования токен должен инвалидироваться.
- Система должна защищать логин, установку пароля и перевыпуск приглашения от перебора и злоупотреблений.
- Ошибки токена должны отображаться без раскрытия внутренних причин отказа.
- При невалидной или просроченной ссылке интерфейс должен сообщать, что ссылка недействительна, и рекомендовать связаться с администратором.
- Система должна вести аудит ключевых действий: создание сотрудника, выпуск и отзыв приглашения, активация, деактивация и административный сброс доступа.
