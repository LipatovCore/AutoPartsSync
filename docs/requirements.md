# Фактические требования к текущей версии

Документ фиксирует, что уже реализовано в коде, а не продуктовые пожелания.

## 1. Назначение системы

Система используется как внутренний веб-инструмент сотрудников магазина автозапчастей.

Подтверждённые сценарии:

- поиск аналогов деталей по артикулу;
- просмотр остатков по найденным аналогам;
- ведение базы клиентов и их автомобилей;
- закрытый доступ сотрудников по email и паролю.

## 2. Пользователи

По коду подтверждены две прикладные роли доступа:

- обычный сотрудник с рабочим доступом;
- администратор, у которого есть permission `employees.manage_employee_access`.

Отдельной бизнес-модели ролей кроме стандартных Django groups/permissions нет.

## 3. Требования к доступу

### Общее

- доступ к рабочим разделам есть только после аутентификации;
- публичной регистрации нет;
- целевая модель пользователя: `employees.Employee`;
- логин выполняется по email и паролю;
- деактивированный сотрудник не должен входить в систему.

### Статусы сотрудника

Сотрудник может находиться в одном из статусов:

- `created`
- `active`
- `deactivated`

### Приглашения

- сотрудника можно создать по email;
- при создании или перевыпуске доступа генерируется одноразовая ссылка установки пароля;
- срок жизни ссылки: 24 часа;
- в БД хранится только hash токена;
- одновременно у сотрудника может быть только одно незавершённое приглашение.

### Установка пароля

- установка пароля доступна по публичной ссылке `/employees/invitations/<token>/set-password/`;
- ссылка должна работать только для валидного токена;
- после успешной установки пароля сотрудник переводится в `active`;
- использованная ссылка становится недействительной;
- автоматический вход после установки пароля не выполняется.

### Административные действия

Администратор может:

- создать сотрудника и приглашение;
- перевыпустить приглашение для сотрудника в статусе `created`;
- сбросить доступ сотруднику в статусе `active`;
- деактивировать сотрудника;
- просматривать журнал аудита доступа при наличии `employees.view_employee_access_audit`.

Администратор не может:

- деактивировать самого себя;
- сбрасывать доступ самому себе.

### Rate limit

Подтверждённые лимиты:

- `login`: 5 попыток за 5 минут, затем блок на 5 минут;
- `password_setup`: 5 попыток за 5 минут, затем блок на 10 минут;
- `invitation_reissue`: 10 попыток за 60 минут, затем блок на 15 минут.

## 4. Требования к разделу поиска аналогов

- маршрут: `/analogs/`;
- поиск выполняется по query-параметру `search`;
- поиск доступен только авторизованному пользователю;
- источник брендов и аналогов: ABCP;
- источник остатков: МойСклад;
- если ABCP возвращает не ровно один бренд, итоговая таблица аналогов не строится;
- в результате показываются артикул, бренд и остаток.

Не подтверждено кодом:

- выбор бренда пользователем из нескольких вариантов;
- сохранение истории запросов;
- кэширование результатов;
- работа с несколькими складами через UI.

## 5. Требования к разделу клиентов и автомобилей

- маршрут списка: `/counterparties/clients/`;
- раздел доступен только авторизованному пользователю;
- используется один workspace-шаблон со списком, карточкой клиента и блоком автомобилей.

### Клиенты

Система должна позволять:

- просматривать список клиентов;
- искать клиентов по имени и телефону;
- создавать клиента;
- редактировать клиента;
- удалять клиента.

Хранимые поля клиента:

- `name`
- `phone`
- `note`

### Автомобили

Система должна позволять:

- создавать автомобиль для клиента;
- редактировать автомобиль;
- удалять автомобиль;
- искать клиента по связанным данным автомобиля.

Хранимые поля автомобиля:

- `brand`
- `model`
- `license_plate`
- `vin`
- `note`

При удалении клиента его автомобили удаляются каскадно.

### Workspace-контракт

Поведение интерфейса зависит от query-параметров:

- `q`
- `client`
- `dialog`
- `car_form`

Это часть текущего контракта UI.

## 6. Требования к аудиту и сессиям

- при активации, деактивации и сбросе доступа серверные сессии сотрудника должны завершаться;
- ключевые действия employee-auth должны попадать в `EmployeeAccessAuditEvent`;
- аудит доступен в Django admin только staff-пользователям с нужным permission.

Подтверждённые типы аудита:

- `employee_created`
- `invitation_issued`
- `invitation_revoked`
- `activation_succeeded`
- `activation_failed`
- `access_reset`
- `employee_deactivated`

## 7. Нефункциональные требования, подтверждённые кодом

- фреймворк: Django 6;
- база данных по умолчанию: SQLite;
- развёртывание поддерживает Gunicorn + Nginx + Docker Compose;
- статика собирается в `src/staticfiles`;
- проект рендерит HTML на сервере, отдельного frontend-приложения нет.

## 8. Что явно не входит в текущую версию

По коду отсутствуют:

- публичная регистрация;
- self-service reset password;
- отправка приглашений по email из системы;
- API для SPA/мобильного клиента;
- заказы, продажи, корзина, счета;
- аналитика и отчёты;
- импорт/экспорт клиентов;
- история изменений клиента;
- полноценное разграничение ролей бизнес-уровня поверх Django groups.
