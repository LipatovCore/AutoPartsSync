# Правила архитектуры

## Общие правила

- Можно:
- Использовать модульную структуру по Django app, если у каждого app есть одна предметная зона ответственности.
- Строить код по цепочке `view/controller -> service -> repository -> model/integration`.
- Держать шаблоны, формы, сервисы, репозитории и интеграции в отдельных модулях.
- Добавлять новый слой только если у него есть четкая ответственность и имя это отражает.
- Нельзя:
- Смешивать HTTP-логику, бизнес-логику, доступ к БД и внешние API в одной функции.
- Создавать "универсальные" модули `utils.py` или `helpers.py` для логики предметной области.
- Копировать одну и ту же бизнес-логику в несколько app.
- Добавлять новый app без отдельной предметной причины.

## Слои

- Можно:
- `view` или `controller` принимать HTTP-запрос, читать параметры, вызывать сервис, подготавливать HTTP-ответ, redirect, render и messages.
- `service` выполнять бизнес-правила, координировать несколько репозиториев и внешних интеграций, определять сценарий операции целиком.
- `repository` читать и изменять данные через Django ORM для одной агрегатной области.
- `model` хранить структуру данных, ограничения, связи, простые инварианты и вычисляемые свойства без сценарной логики.
- `forms` использовать для валидации входных данных HTML-форм.
- `integration` выносить работу с ABCP, МойСклад и другими внешними API в отдельные модули или классы.
- Нельзя:
- Помещать бизнес-логику в `views.py`.
- Выполнять ORM-запросы из шаблонов.
- Вызывать внешние API прямо из `view`.
- Обращаться к `request`, `messages`, `redirect`, `render` и `reverse` из `service` и `repository`.
- Помещать SQL, HTTP-запросы и работу с `.env` в `forms` и `models`.

## Правила для controller и view

- Можно:
- Держать в `view` только разбор входных параметров, выбор HTTP-статуса, вызов сервиса и сбор контекста шаблона.
- Делать явную проверку типа запроса через декораторы наподобие `@require_POST`.
- Передавать в сервис уже очищенные и явно названные параметры.
- Нельзя:
- Строить сложные `Q`, `annotate`, `prefetch_related` и сценарии записи в `view`, если эта логика нужна не для одного шаблона, а для бизнес-операции.
- Делать больше одного бизнес-сценария в одном `view`.
- Ловить и "глушить" все исключения без перевода их в понятную ошибку уровня сценария.

## Правила для service

- Можно:
- Делать сервисы основным местом бизнес-логики.
- Возвращать из сервиса данные, нужные `view`, в явной структуре.
- Создавать отдельный сервис на отдельный сценарий: поиск аналогов, создание клиента, обновление автомобиля, удаление клиента.
- Открывать транзакцию в сервисе, если операция меняет несколько сущностей.
- Нельзя:
- Хранить в сервисе детали HTML, шаблонов и query-параметров интерфейса.
- Вызывать сервис из другого сервиса без явной необходимости; общую логику нужно выносить в отдельный доменный сервис.
- Возвращать из сервиса `HttpResponse`, `redirect` или объект `request`.

## Правила для repository

- Можно:
- Инкапсулировать ORM-запросы в `repository`, если они повторяются или содержат нетривиальную выборку.
- Давать репозиториям предметные имена: `client_repository`, `car_repository`.
- Держать методы репозитория короткими и ориентированными на одну задачу выборки или записи.
- Нельзя:
- Размещать в репозитории бизнес-решения уровня сценария.
- Смешивать в одном репозитории работу с БД и внешними HTTP API.
- Создавать "базовый репозиторий" с абстракциями, которые не нужны минимум двум реальным модулям.

## Правила работы с моделями

- Можно:
- Хранить в моделях ограничения полей, связи, `Meta`, `__str__` и простые проверки, напрямую относящиеся к сущности.
- Добавлять индексы, `unique` и ограничения на уровне модели и миграций, если правило относится к данным.
- Использовать `TextChoices` или `IntegerChoices` для фиксированных наборов значений.
- Нельзя:
- Помещать в модель сетевые вызовы, обращение к настройкам интеграций и сложные сценарии изменения нескольких сущностей.
- Помещать в модель код, который зависит от HTTP-запроса или шаблона.
- Использовать сигналы Django для основной бизнес-логики; сигналы допустимы только для технических побочных действий, которые не критичны для сценария.

## Правила работы с БД

- Можно:
- Работать с БД только через Django ORM и миграции.
- Добавлять миграцию вместе с каждым изменением схемы.
- Использовать `select_related` и `prefetch_related`, если это подтверждено реальной потребностью выборки.
- Заворачивать многозаписные изменения в `transaction.atomic()`.
- Делать ограничения данных на уровне схемы, если нарушение недопустимо по бизнес-правилу.
- Нельзя:
- Менять схему БД вручную без миграции.
- Писать сырые SQL-запросы без крайней необходимости и без комментария, почему ORM недостаточен.
- Держать N+1 запросы в коде, если выборка используется на списках или карточках.
- Сохранять в БД данные внешних API "на всякий случай" без явного сценария хранения.
- Выполнять запись в БД из шаблона, админского action без сервиса или из клиентского JavaScript в обход серверной валидации.

## Правила внешних интеграций

- Можно:
- Выносить ABCP и МойСклад в отдельные интеграционные модули или классы-клиенты.
- Хранить URL, токены и логины только в настройках и переменных окружения.
- Задавать timeout для каждого HTTP-запроса.
- Преобразовывать ответы внешних API в внутренние структуры до возврата в сервис.
- Нельзя:
- Вызывать `requests.get()` и `requests.post()` из `views.py`.
- Хардкодить токены, логины, пароли, `storeId` и другие идентификаторы в коде.
- Возвращать "сырой" ответ внешнего API прямо в шаблон.
- Использовать `print()` для обработки ошибок интеграций.

## Правила логирования и ошибок

- Можно:
- Использовать стандартный `logging`.
- Поднимать свои исключения уровня сценария или интеграции, если нужно отделить тип ошибки.
- Показывать пользователю краткое сообщение, а технические детали оставлять в логах.
- Нельзя:
- Использовать `print()` вместо логирования.
- Прятать ошибку и продолжать сценарий, если из-за этого данные становятся недостоверными.
- Логировать секреты, токены, пароли и полный дамп чувствительных данных.

## Правила тестирования

- Можно:
- Добавлять тесты на каждый новый сервис, репозиторий и нетривиальный `view`.
- Проверять отдельно бизнес-правила сервиса и отдельно HTTP-поведение `view`.
- Мокать внешние API на границе интеграционного слоя.
- Нельзя:
- Добавлять новую бизнес-логику без теста.
- Проверять сервис только через шаблон, если можно проверить его напрямую.
- Ходить в реальные внешние API из автотестов.

## Правила добавления зависимостей

- Можно:
- Добавлять зависимость только если задача не решается стандартной библиотекой Python, Django или уже установленными пакетами.
- Перед добавлением фиксировать цель зависимости в PR или описании задачи.
- Добавлять пакет с закрепленной версией в `requirements.txt`.
- Проверять, что библиотека поддерживается, совместима с текущей версией Python и не дублирует уже существующий пакет.
- Нельзя:
- Добавлять пакет "на будущее".
- Добавлять несколько библиотек для одной и той же задачи без явной причины.
- Подтягивать тяжелый фреймворк ради одной мелкой функции.
- Использовать зависимость без обновления `requirements.txt`.

## Правила изменений архитектуры

- Можно:
- При переносе логики из `view` в `service` оставлять поведение интерфейса без изменений, если задача не требует обратного.
- Рефакторить по шагам: сначала выделять сервис, затем репозиторий, затем покрывать тестами.
- Документировать новое архитектурное правило в `docs`, если оно становится обязательным для всей команды.
- Нельзя:
- Смешивать рефакторинг архитектуры с несвязанным функциональным изменением в одном небольшом коммите.
- Вводить новый паттерн в одном app и противоположный паттерн в другом app.
- Нарушать этот документ без явного обновления самого документа.
