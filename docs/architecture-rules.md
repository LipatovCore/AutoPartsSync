# Правила разработки и архитектурные ограничения

Документ задаёт правила для новых изменений. Он не переписывает историю проекта: если в коде уже есть отклонения, они перечислены как исключения, а не как норма для новых задач.

## 1. Базовый принцип

Новый код должен продолжать существующую архитектуру конкретного модуля, а не подменять её случайным новым паттерном.

### Разрешено

- расширять существующий паттерн внутри приложения;
- выделять новый слой только когда появляется повторяемая логика;
- документировать архитектурный долг без скрытого рефакторинга.

### Запрещено

- выдумывать новый доменный слой без реальной необходимости;
- переносить логику между приложениями "для красоты";
- менять UX-контракты query string в `counterparties` без полной проверки.

## 2. Правила по слоям

### `config`

Здесь можно:

- настройки Django;
- env parsing;
- подключение приложений;
- root routing.

Здесь нельзя:

- бизнес-логику;
- код интеграций;
- ORM-запросы предметной области.

### `views`

Здесь можно:

- читать query string и POST;
- создавать формы;
- вызывать сервисы или ORM;
- записывать `messages`;
- делать `render` и `redirect`.

Здесь нельзя:

- добавлять новую тяжёлую бизнес-логику, если её можно выделить в сервис;
- вызывать внешние API из новых view-функций;
- работать с `.env` напрямую, кроме уже существующих мест, которые пока не рефакторились.

Исключения из текущего кода:

- `analogs.views` уже нарушает это правило;
- `counterparties.views` уже содержит заметную долю прикладной логики.

Новые изменения не должны усиливать эти нарушения.

### `services`

Используются сейчас только в `employees`.

Здесь нужно размещать:

- бизнес-сценарии;
- координацию нескольких операций;
- транзакции;
- инвалидацию сессий;
- аудит;
- rate limit.

Из сервиса нельзя:

- возвращать `HttpResponse`;
- зависеть от `request`, `messages`, `render`, `redirect`;
- писать HTML-зависимую логику.

### `repositories`

Сейчас есть только в `employees`.

Здесь нужно размещать:

- переиспользуемые ORM-операции;
- выборки, которые нужны нескольким сервисам;
- короткие CRUD-операции уровня данных.

Из repository нельзя:

- вызывать внешние API;
- принимать решения уровня бизнес-сценария;
- тянуть в себя HTTP-слой.

### `models`

Здесь допустимы:

- поля;
- связи;
- `Meta`;
- индексы и constraints;
- простые свойства сущности.

Здесь не должно быть:

- сетевых вызовов;
- `request`-зависимой логики;
- сценариев, которые меняют несколько агрегатов сразу.

### `forms`

Использовать для:

- валидации пользовательского ввода;
- виджетов и placeholder;
- ошибок формы.

Не использовать для:

- интеграций;
- транзакционных сценариев;
- скрытой записи связанных сущностей.

## 3. Правила по приложениям

### `employees`

Новый код должен сохранять паттерн:

`views -> services -> repository -> models`

Практические правила:

- новую бизнес-логику employee-auth писать в `services`;
- ORM-логику, которая повторяется, выносить в repository;
- permission-правила держать в `permissions.py`;
- view оставлять тонкими.

### `counterparties`

Текущий паттерн:

`models + forms + function-based views + templates + admin`

Практические правила:

- поля клиентов и автомобилей добавлять через `models.py` и `forms.py`;
- поисковую и workspace-логику менять осторожно в [`src/counterparties/views.py`](/C:/Users/lipyf/GitHub/AutoPartsSync/src/counterparties/views.py);
- если появляется повторяемый бизнес-сценарий, допустимо вынести его в отдельный сервис, но без массового рефакторинга всего модуля;
- нельзя ломать параметры `q`, `client`, `dialog`, `car_form`.

### `analogs`

Текущий паттерн:

`function-based view + helper functions in the same module`

Практические правила:

- не добавлять ещё больше побочных обязанностей в `search`;
- новые интеграционные вызовы по возможности выносить в отдельный модуль;
- если меняется поиск, сначала проверить, как он зависит от ответа ABCP по брендам;
- не хардкодить новые секреты, URL и идентификаторы.

## 4. Где писать бизнес-логику

### Нужно писать

- в `employees/services/*` для сценариев доступа сотрудников;
- в новых service-модулях, если в `counterparties` или `analogs` появляется повторяемая прикладная логика;
- в моделях только простые ограничения уровня данных.

### Не нужно писать

- в шаблонах;
- в `admin.py`, если это не чисто админская настройка;
- в `config`;
- в `print()` и ad-hoc утилитах.

## 5. Где писать валидацию

HTML-формы:

- в `forms.py`.

Ограничения данных:

- в `models.py` и миграциях.

Сценарные проверки:

- в сервисах.

Не делать:

- дублировать одну и ту же проверку в template и view как единственный источник истины;
- прятать бизнес-ошибки только в template.

## 6. Работа с моделями

### Нужно

- добавлять миграцию на каждое реальное изменение схемы;
- использовать `ForeignKey`, indexes и constraints там, где правило относится к данным;
- явно описывать каскадное удаление и его последствия в документации.

### Нельзя

- менять схему без миграции;
- использовать сырые SQL-запросы без крайней необходимости;
- записывать данные внешних API в БД "на будущее", если это не подтверждено задачей.

## 7. Работа с API, view и шаблонами

### API и внешние сервисы

- использовать `requests` с `timeout`, как уже сделано;
- конфигурацию брать из `settings` или env, а не из захардкоженных значений;
- ошибки логировать через `logging`, не через `print()`.

### View

- держать короткими;
- не смешивать несколько независимых сценариев в одном обработчике без необходимости;
- если нужен сложный redirect-flow, оформлять его явно и документировать query-параметры.

### Шаблоны

- не помещать в шаблон бизнес-правила;
- можно держать UI-логику показа/скрытия блоков;
- при больших правках не разносить inline JS/CSS хаотично по нескольким шаблонам.

## 8. Антипаттерны

Запрещено добавлять:

- новые `utils.py` или `helpers.py` как свалку доменной логики;
- прямые вызовы внешних API из нового view-кода;
- захардкоженные токены, пароли, URL и store identifiers;
- дублирование одного и того же сценария в нескольких приложениях;
- скрытый рефакторинг архитектуры под видом "небольшой правки".

Нежелательно оставлять без отдельной задачи:

- расширение `analogs.views` новыми обязанностями;
- увеличение плотности логики в `counterparties.views`;
- дальнейшее разрастание inline-стилей в базовом layout.

## 9. Стандарты структуры и именования

### Файлы

- модели: `models.py`
- формы: `forms.py`
- маршруты: `urls.py`
- административная регистрация: `admin.py`
- бизнес-сценарии: `services/<scenario>_service.py`
- ORM-обвязка: `repositories/<entity>_repository.py`

### Имена

- Python-идентификаторы на английском;
- пользовательские тексты и `verbose_name` могут быть на русском;
- service и repository называть по сценарию или доменной области, а не абстрактно.

## 10. Как добавлять новую фичу

1. Найти модуль, которому действительно принадлежит поведение.
2. Проверить, какой паттерн в нём уже используется.
3. Добавить изменение в тот же слой, если логика небольшая.
4. Если логика начинает повторяться, выделить сервис или repository точечно.
5. Обновить документацию и `todo.md`.
6. Запустить `manage.py check` и `manage.py test`.
7. Проверить затронутый UI-сценарий вручную.

## 11. Как не ломать архитектуру

- не менять сразу и поведение, и паттерн хранения логики;
- не переносить код между app без явной причины;
- не менять существующие URL и query-параметры ради "чистоты";
- не документировать желаемое состояние как будто оно уже реализовано.
