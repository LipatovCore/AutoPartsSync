# Правила разработки

## Статус документа

Это обязательный рабочий документ для текущей кодовой базы. Он описывает правила безопасной работы с уже существующим Django-проектом, а не идеальную целевую архитектуру.

## Именование

- Имена модулей, классов, функций, переменных и URL names использовать на английском.
- Пользовательские тексты, `verbose_name`, подписи форм и сообщения интерфейса могут быть на русском.
- Не переименовывать существующие модули, шаблоны, URL names и query parameters без отдельной задачи на совместимость.

## Организация модулей

- `src/config/` отвечает только за инфраструктуру Django.
- `src/counterparties/` отвечает только за клиентов и автомобили.
- `src/analogs/` отвечает только за поиск по артикулу и внешние интеграции.
- Новые шаблоны добавлять в `src/templates/` или в app-specific подпапку.
- Новые management commands добавлять только при реальной потребности и только как отдельное осознанное расширение проекта.

## Разделение ответственности

- Модели хранят структуру данных.
- Формы отвечают за валидацию пользовательского ввода в CRUD-сценариях.
- Views управляют request/response flow.
- Шаблоны отвечают за отображение, но не за новую нетривиальную бизнес-логику.
- Интеграционный код не должен появляться в шаблонах, admin или `config`.

Если логика в view становится объемной или повторяется, ее нужно выносить в отдельный модуль внутри того же app целиком. Нельзя оставлять смесь из дублированной логики, полу-вынесенных функций и прямых копий по нескольким views.

## Где должна жить логика

### `counterparties`

- CRUD-логика остается в `views.py` и `forms.py`.
- ORM-запросы к `Client` и `Car` остаются внутри `counterparties`.
- Доменные правила для клиентов и автомобилей не должны появляться в `config`.

### `analogs`

- Логика внешних HTTP-запросов остается внутри `analogs`.
- Код поиска по артикулу не должен разноситься по другим apps.
- Нельзя смешивать код интеграций `analogs` с кодом клиентского workspace.

## Правила для ORM и запросов

- ORM-запросы размещать рядом с app, которому принадлежат данные.
- Не дублировать одну и ту же ORM-конструкцию по нескольким views.
- При росте сложности запроса выносить его в отдельную функцию внутри того же app.
- Использовать `select_related` и `prefetch_related`, если это нужно для реально используемых связанных объектов.
- Не переносить доступ к доменным моделям в `src/config/`.

## Правила для views / forms / serializers / сервисных модулей

- Использовать существующий подход с function-based views.
- Новые защищенные страницы обязательно помечать `@login_required`.
- Для CRUD по Django-моделям использовать `ModelForm`, как в `counterparties`.
- В проекте нет serializers и DRF; не вводить их локально в одном месте.
- Отдельные сервисные модули допустимы только как целостное упрощение логики внутри одного app. Нельзя создавать псевдо-архитектуру с одним случайным `services.py`.

## Правила тестирования

- Каждый change set обязан прогонять:
  - `python manage.py check`
  - `python manage.py test`
- Отсутствие тестов в репозитории не освобождает от ручной проверки.
- Если изменение не тривиально, нужно добавить хотя бы минимальные Django tests.
- Изменения в шаблонах и пользовательских сценариях проверять вручную в браузере.
- Для `analogs` проверять:
  - пустой результат;
  - ошибку внешнего API;
  - базовый успешный сценарий.
- Для `counterparties` проверять:
  - поиск;
  - создание;
  - редактирование;
  - удаление;
  - сохранность query parameters `q`, `client`, `dialog`, `car_form`.

## Правила миграций

- Миграции создавать только при изменении моделей.
- Уже примененные миграции не редактировать без отдельного решения.
- При изменении модели проверять:
  - `makemigrations`
  - `migrate`
  - формы
  - admin
  - затронутые шаблоны
- Если изменение модели меняет смысл доменной сущности, это должно быть отражено в документации.

## Правила логирования и обработки ошибок

- Не использовать `print(...)` для нового прикладного кода.
- Для пользовательских ошибок использовать понятный UI feedback.
- Для внутренних и интеграционных ошибок оставлять developer-visible сигнал.
- Ошибки внешних API не должны теряться без следа.
- Новые hardcoded identifiers, токены, store IDs и environment-specific значения запрещены.

## Правила конфигурации

- Секреты и токены брать только из env vars.
- Новый env var нужно в том же change set:
  - упомянуть в `README.md`;
  - добавить в `docs/runbook.md`;
  - добавить в `docs/ai-context.md`, если он влияет на работу агента.
- Настройки Django менять через `src/config/settings.py`.
- Не размещать environment-specific magic values прямо во views.

## Правила документации

Документацию обязательно обновлять, если меняется:

- структура apps;
- команда запуска;
- env/config;
- архитектурное правило;
- доменная модель;
- интеграционный контракт;
- известный риск;
- правила для будущих агентов.

Минимум для проверки:

- `README.md`
- релевантный файл в `docs/`
- `docs/ai-context.md`, если меняются правила работы агента
- `.codex/working-rules.md`, если меняются устойчивые рабочие правила

## Запрещенные практики

- Нельзя документировать несуществующие заказы, закупки или поставщиков как текущую функциональность.
- Нельзя добавлять случайный REST API рядом с server-rendered flow.
- Нельзя переносить бизнес-логику в `config`.
- Нельзя рефакторить `src/analogs/views.py`, `src/counterparties/views.py`, `src/templates/counterparties/client_list.html` и `src/templates/base.html` без проверки полного пользовательского сценария.
- Нельзя менять query parameters `q`, `client`, `dialog`, `car_form` без проверки всего workspace flow.
- Нельзя считать `src/staticfiles/` местом для прикладной разработки.
- Нельзя считать README источником истины, пока утверждение не подтверждено кодом.
- Нельзя менять кодировку существующих файлов “по пути”; если проблема с UTF-8 подтверждена, ее нужно исправлять отдельной задачей.
