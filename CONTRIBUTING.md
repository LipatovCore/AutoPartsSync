# CONTRIBUTING

## Назначение документа

Этот репозиторий уже содержит рабочий Django-код и интеграции с внешними API. Вклад должен сохранять текущее поведение системы, не расширять продуктовую область без подтверждения и не подменять реальные факты архитектурными предположениями.

## Локальная подготовка

Ожидается, что разработчик:

- работает из корня репозитория;
- использует виртуальное окружение Python;
- имеет локальный `.env` с нужными переменными окружения;
- понимает, что часть функциональности зависит от внешних API ABCP и МойСклад.

Базовая подготовка:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
cd src
..\.venv\Scripts\python.exe manage.py migrate
```

## Стандарты кодирования

Следовать текущему стилю репозитория, а не навязывать новый:

- Python identifiers и имена модулей оставлять на английском;
- пользовательские тексты и `verbose_name` допускаются на русском;
- для Django CRUD использовать `ModelForm`, если уже работаете в приложении `counterparties`;
- в приложении `counterparties` придерживаться текущего паттерна `models + forms + function-based views + templates + admin`;
- в приложении `analogs` учитывать, что логика сейчас сосредоточена в `views.py`; новые изменения должны быть аккуратными и не ломать внешний flow;
- шаблоны должны оставаться совместимыми с существующим `base.html` и Django messages.

## Ожидания по тестированию

В репозитории нет автоматических тестов, но каждое изменение должно сопровождаться проверками:

- `python manage.py check`
- `python manage.py test`
- ручная проверка затронутого пользовательского сценария

Если изменение затрагивает:

- модели или миграции - проверить создание, чтение, редактирование и удаление данных;
- поиск аналогов - проверить, что страница корректно обрабатывает пустой результат и ошибку внешнего API;
- шаблоны - проверить отображение на страницах `/analogs/`, `/counterparties/clients/`, `/accounts/login/`.

Если вы добавляете новый нетривиальный код, нужно добавить хотя бы минимальные тесты, а не расширять количество непроверяемой логики.

## Ожидания по документации

Документацию нужно обновлять вместе с кодом, если изменение затрагивает:

- новый env var;
- новую интеграцию;
- новый Django app;
- новые команды запуска;
- новые миграции, критичные для rollout;
- новую архитектурную договоренность;
- новое ограничение или риск.

Минимум для синхронизации:

- `README.md`
- один или несколько файлов из `docs/`
- `.codex/working-rules.md`, если меняются устойчивые правила работы для агентов

## Безопасный workflow изменений

1. Изучить:
   - `README.md`
   - `docs/architecture.md`
   - `docs/development-rules.md`
   - `docs/decisions-and-debt.md`
2. Найти фактическую точку изменения в коде.
3. Проверить связанные шаблоны, формы, URL и admin.
4. Вносить минимально необходимое изменение.
5. Выполнить `manage.py check` и `manage.py test`.
6. Вручную проверить затронутый пользовательский сценарий.
7. Обновить документацию.

## Checklist перед review

- Изменение основано на коде, а не на предположении о продукте.
- Не добавлены неподтвержденные сущности или процессы.
- Не сломан существующий flow авторизации.
- Не изменены query parameters, управляющие workspace клиентов, без явной причины.
- Новые env vars задокументированы.
- Миграции добавлены только при реальном изменении моделей.
- Сообщения об ошибках не сводятся к `print(...)`, если можно дать пользователю и разработчику более полезный сигнал.

## Review checklist

- Соответствует ли изменение текущей архитектуре Django monolith?
- Находится ли логика в ожидаемом месте для этого приложения?
- Не увеличилась ли связность между `analogs` и `counterparties` без необходимости?
- Не появились ли новые hardcoded значения, аналогичные текущему `storeId`?
- Не разошлась ли документация с кодом?
- Появились ли хотя бы минимальные проверки для нового поведения?
- Не принята ли проблема отображения текста в терминале за реальную проблему содержимого файла?

## AI-assisted contributions

AI-инструменты допустимы, но для них действуют дополнительные правила:

- нельзя добавлять несуществующие бизнес-процессы;
- нельзя писать документацию по обещанному scope, если он не подтвержден кодом;
- перед правками обязательно читать `docs/ai-context.md` и `.codex/working-rules.md`;
- любые assumptions должны быть явно помечены как `Assumption`, `Unknown` или `Needs verification`;
- AI не должен массово рефакторить архитектуру без отдельного решения человека;
- после AI-правок человек обязан проверить команды запуска и затронутые пользовательские сценарии.
